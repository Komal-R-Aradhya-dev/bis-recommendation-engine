WHAT THE APPLICATION DOES
A working web app that helps Indian procurement users obtain Indian Standards recommendations.
A signed-in user can:
1. Type a procurement query and/or upload a tender PDF/DOCX.
2. Send that request to the backend, which forwards it to an external RAG/LLM service.
3. View extracted tender requirements, a summary, recommended Indian Standards, warnings, and expandable evidence/certification/testing/procurement details.
4. Download a PDF report generated from a saved history record.
5. Re-open previous analyses from a sidebar history list (restored from MongoDB; no second recommendation API call).
6. Toggle light/dark theme and sign out.

This is NOT a multi-turn chat product. frontend/src/types/chat.ts explicitly says there is no conversationId, no follow-up Q&A, and no message chaining. Home only shows one active analysis at a time.

TARGET USERS
- Primary: procurement officials.
- Backend User.role enum is ["procurement_official", "admin"] with default "procurement_official" (backend/src/models/User.js).
- The frontend displays role as a string badge/field. There is no admin-only UI, no role-based route, and no role-based feature gating in the frontend.
- Secondary audience implied by branding: Government of India / Bureau of Indian Standards stakeholders and hackathon judges.

PRIMARY USER WORKFLOW
Register or Login
→ Protected Home shell (Sidebar + TopBar + Composer)
→ Submit query and/or PDF/DOCX
→ Loading / analyzing state (abortable)
→ Results: query, summary, tender requirements, recommendation cards, warnings
→ Optional: Download PDF report
→ Optional: New Analysis (clears current result)
→ Optional: click a sidebar history item to restore a previous result
→ Optional: Settings / Sign out

API ARCHITECTURE
REST over HTTP. Frontend axios instance baseURL is:
  import.meta.env.VITE_API_URL || "/api"
Vite dev proxy (frontend/vite.config.ts):
  "/api" → http://localhost:5000
So in local dev, browser calls /api/... and Vite forwards to Express /api/...

Envelope used by JSON endpoints:
  { success: boolean, message?: string, data?: ..., errors?: ... }

Auth header:
  Authorization: Bearer <token>

AUTHENTICATION MECHANISM
- Register/Login return { token, user: { id, name, email, role } } inside data.
- Frontend stores JWT in localStorage key "bis_auth_token" (frontend/src/services/api.ts).
- Frontend persists user object in Zustand persist key "bis-auth-user".
- Axios request interceptor attaches the Bearer token.
- Axios response interceptor clears the token on HTTP 401. It does NOT clear the Zustand user.
- Route guards in frontend/src/routes/AppRoutes.tsx:
  - ProtectedRoute: if missing token OR missing user → Navigate to /login
  - PublicRoute: if token AND user exist → Navigate to /
- JWT is signed with { id, role }, expires in 7 days (backend/src/services/auth.service.js).
- No refresh-token flow. No OAuth. No cookies.

DATABASE
MongoDB collections via Mongoose models:
- User: name, email, password, role, timestamps
- RecommendationHistory: user, query, language, hasDocument, ragResponse (Mixed), timestamps

EXTERNAL INTEGRATION
Backend RAG client:
- Text query: POST {RAG_API_URL}/recommend/llm (application/x-www-form-urlencoded: query, limit)
- Tender file: POST {RAG_API_URL}/recommend/llm/tender (multipart: file, optional query, limit)
- Timeout: RAG_TIMEOUT_MS = 1,200,000 ms (20 minutes)
- RAG_API_KEY is loaded in backend/src/config/env.js and backend/src/config/rag.js but is NOT sent in rag.service.js request headers.

SECTION 9 — PROTECTED FUNCTIONALITY
==================================================

The redesign must not break any of the following.

BACKEND ENDPOINTS (do not change; frontend must keep calling them)

GET /
- Health string "BIS Recommendation Engine API is running"
- Frontend does not call this.

POST /api/auth/register
- Body: { name, email, password }
- Validates name>=2, email regex, password>=6
- 201 { success, message, data: { user:{id,name,email,role}, token } }
- 400 { success:false, errors }
- 409 Email is already registered
- Depends: Register.tsx → useAuth.register → auth.api.register → setToken + setUser

POST /api/auth/login
- Body: { email, password }
- 200 same data envelope
- 401 Invalid email or password
- Depends: Login.tsx → useAuth.login → auth.api.login

POST /api/recommendations
- Auth Bearer required
- Rate limit: 30 / 15 min
- JSON { query, limit } OR multipart query + document + limit
- File: field name "document"; PDF/DOCX; 10MB
- 400 if neither query nor file
- 200 { success, message, data: { ...ragResponse, historyId } }
- Depends: Composer → Home.handleSubmit → useRecommendations.generate → recommendation.api.submitRecommendation
- Do not change limit 5, field names, or abort signal wiring

GET /api/recommendations/history
- Auth required
- Returns up to 20 latest RecommendationHistory docs for req.user.id
- Shape per item: _id, user, query, language, hasDocument, ragResponse, createdAt, updatedAt
- Depends: useHistory → history.api.fetchHistory → Sidebar
- Normalization in history.api.ts must keep working

DELETE /api/recommendations/history/:id
- Auth + ownership
- Implemented in backend and history.api.deleteHistory
- NOT used by any UI. Do not build a delete control that changes the API. If you add UI delete later, that is a feature, not this redesign’s job, unless explicitly requested.

POST /api/reports
- Auth required
- Body: { historyId } valid ObjectId owned by user
- Response: application/pdf binary, Content-Disposition attachment
- 400/404 JSON errors
- Depends: Home.handleDownloadReport → report.api.downloadRecommendationReport
- Frontend expects a Blob. Do not parse as JSON.

API REQUEST/RESPONSE CONTRACTS
- Keep axios baseURL behavior (VITE_API_URL || "/api")
- Keep Authorization header injection
- Keep AuthApiResponse.data unwrap
- Keep Recommendation response fields listed in frontend/src/types/recommendation.ts
- Keep historyId on generate and restore
- Auth 400 uses `errors` object, not `message`. Do not assume message exists.

AUTHENTICATION
- localStorage "bis_auth_token"
- Zustand persist "bis-auth-user"
- 7-day JWT
- 401 interceptor clears token only
- Login/Register must still set both token and user or the next ProtectedRoute will bounce

AUTHORIZATION
- All recommendation/history/report routes use protect middleware
- Ownership is server-side (history user match)
- Frontend must not strip the header or send another user’s historyId (UI just uses store/item ids)

DATABASE INTERACTIONS
- Frontend never talks to Mongo.
- Creating history happens only inside processRecommendationRequest after RAG returns.
- Do not add client-side fake history rows.

STATE MANAGEMENT
- authStore, themeStore persist keys
- recommendationStore result/historyId
- Do not persist recommendation results unless you also keep historyId accurate
- Do not introduce a second user store

ROUTING
- Paths /login /register / /settings and * → /
- Public vs protected gates
- Success auth → /
- Logout → /login replace
- History/New Analysis → /

FORM SUBMISSION BEHAVIOR
- preventDefault on all three forms
- Login/Register required fields
- Register minLength 6
